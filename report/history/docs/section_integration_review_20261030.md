# 截面测量集成只读审查

审查对象：最终整板构建启动后的冻结源码。仅阅读源码并新增本报告；未修改 RTL、约束或运行时，未运行仿真、综合、实现和板端命令。主代理正在进行的 19+4 集成测试不计为本报告新证据。

## 结论

未发现正常单包串行调用路径中的地址译码、暂存写入对齐、组合读口或几何握手接入错误。截面模块是旁路观察者，不给 primary 流增加背压。其使用条件是：配置在包间完成；每次等待 0x750 发布并读取完整结果，再提交下一包；取消或失败后不得把仍可能发布的旧结果当作新会话结果。

本结论是静态接口审查，不能替代最终整板时序、集成回归、板上寄存器一致性及实际速度验收。

## 必须保留的使用限制

### 1. 截面模块只有一份点存储，不接重叠包

section_measure.sv:94、319、325–340、346 明确规定：求解期间的有效点计入 dropped；忙时的 commit 不排队。因此 primary 成功不代表截面求解一定覆盖了每个 primary 包。0x79C 为累计 dropped；0x750 为发布计数，不是原 primary frame ID。

当前调用路径满足串行条件：live.py:641–650 消费 warm-up 的截面发布；正式循环先在 live.py:703 调用 pfo3.run，再在 755 等待 section.frame，之后才进入下一次循环。PLSection.frame（pl_section.py:124–169）要求恰好下一个计数、读完表后二次核对计数，并用 dropped_delta 标记无效。capture worker 只准备 Raw，不会另行提交 PFO3。

后续增加 PFO3 并行队列时不能直接复用这个调用合同，需增加硬件双缓冲/包身份或继续维持截面串行。

### 2. 配置没有硬件帧内锁或影子提交

section_measure.sv:289–305 的配置写在任意求解状态均可发生。中途改变原点、方向、Z 窗口、阈值或 enable，可能使同一帧混用配置或使求解未提交。这不是 r35_axi 的暂存错拍，而是接口合同限制。

当前 configure 在 warm-up 前完成（live.py:516–520），自动 Z 窗口更新在 section.frame 返回后执行（live.py:755–759；pl_section.py:109–121），符合要求。运行期间不得另起 MMIO 工具改这些寄存器。读取表时写 0x744 选择器属于读表操作，不改变求解阈值。

### 3. discard 不是求解器取消或会话清零

section_measure.sv:341 只在 S_COLLECT 接受 discard，求解阶段仍会完成并增加 r_packets；enable=0 也只停止新点采样，不取消已有求解。还有一个边界：若旧 pend 已为 1、管线已空，S_COLLECT 中的 discard 清零与后面的求解状态 case（461）不是互斥结构，后者仍可按旧 pend 进入求解。该边界是静态识别的风险，本报告未新增测试确认。

正常串行路径不在这个窗口提交新 START。取消、DMA 错误或超时后应保留错误并结束当前会话；不能立即重用同一计数基准假定旧求解已丢弃。重新加载/复位后的新会话，或明确排空并重新建立计数基准后才可继续。该限制应保留在板端故障测试和说明中。

### 4. 发布快照需由软件避免下一次发布覆盖

表在 S_PUB_W 逐行更新，最后 S_PUB_END 才同时更新标量和 r_packets（section_measure.sv:885–908）。这保证“新 counter 出现后，当前表已写完”；它不是双缓冲快照。读取过程中如果允许另一个包求解发布，仍可能混表；当前软件的串行提交和读后 counter 核对规避该问题。

本次未发现需要在最终构建过程中改 RTL 的正常集成错误。上述限制应通过单包调用纪律和最终故障验证保持，不能据本报告声称已完成板上验收。原 195 包逐位回归、乘法器 4105 例及 OOC 结果引用已有证据，本次未重跑；最终 19+4、整板实现与现场验证由主代理汇总。

## 本次 60 秒静态运行的准入解释

在同一调用者、无取消后自动重试、逐包等待并读取截面结果、配置只在包间更新的前提下，上述静态发现不阻断本次正常 60 秒静态测试。wrapper 软停只请求主循环退出，当前迭代完成后再 cleanup，也不等于向求解器注入异步 abort。实际寄存器一致性和吞吐仍要由该现场测试验证，不能预写通过。

`disable()` 只向 0x704 写零：它停止新的 `take`，但既不清已采集点，也不取消 `pend` 或求解器。若在 commit 之前禁用，该 commit 不会启动求解；若已经 pend/求解，仍可能完成发布。正常退出的用法是在当前帧的 `section.frame()` 已返回后 disable。错误路径中则结束会话、不消费后续旧发布、不自动重试；需要重新建立硬件和 packet 基准后才能恢复。

## 求解周期的证据分层

- **已运行的历史证据，非本次重跑：**读取最终 `evidence/section_fix10_full195.json`，20 组共 195 包中的最大 `max_solve_cycles` 为 `reversed` 的 **115,418 拍**，100MHz 对应约 **1.15418ms**。这只是已测样本最大值，不是任意输入最坏值。
- **本次只读推导：**点数上限 N=1024、分段上限 16；插入排序有界（保守按 `4*N*N` 拍计）；中值各 32 次扫描，中值调用上限为 `2+15+16+1=34`（spacing、noise、相邻差、参考差及主台阶）。保守把每次中值计为 `64*(N+64)` 拍，再为所有其它扫描、最多两遍拟合、算术握手和表发布预留 1,000,000 拍，得到 `4*1024*1024 + 34*64*(1024+64) + 1,000,000 = 7,561,776` 拍，即在 **8,000,000 拍（80ms@100MHz）**保守预算内。
- 上述是正常内部状态、时钟持续、配置不在帧内改变时的源码预算，不是形式化 WCET 证明，也不是板测实测。乘法为固定流水，除法最多 64 次迭代，平方根 32 次迭代；不存在等待外部 ready 的求解状态。PLSection 的默认 2 秒等待期限远大于该正常输入预算，但失钟、寄存器破坏和异常重入不在此推导内。
- 新增 DSP 和流水可能改变 solve_cycles，因此不能用旧版本周期预测最终整板吞吐；数值等价与周期指标应分别报告。
